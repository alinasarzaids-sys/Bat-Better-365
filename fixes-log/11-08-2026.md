# Fixes: dependency versions & Metro bundling crash

Date: 2026-08-11

Three separate issues were found and fixed while getting the app running again.

## 1. Dependencies out of sync with installed Expo SDK

`expo-doctor`/`expo install --check` flagged several packages as mismatched with
Expo SDK 53:

| Package | Was | Now |
|---|---|---|
| `@expo/metro-runtime` | 5.0.4 | ~5.0.5 |
| `@react-native-community/datetimepicker` | 8.6.0 | 8.4.1 |
| `expo-image` | 2.2.1 | ~2.4.1 |
| `expo-router` | 5.0.7 | ~5.1.11 |
| `expo-web-browser` | 14.1.6 | ~14.2.0 |
| `react-native` | 0.79.3 | 0.79.6 |
| `expo-modules-autolinking` | 57.0.9 | ~2.1.0 |
| `@react-native-picker/picker` | 2.11.0 | 2.11.1 |
| `expo-screen-capture` | 7.1.5 | ~7.2.0 |
| `@react-navigation/*` | unpinned/stale | `^` ranges matching SDK 53 |

**Why:** Expo SDK releases are tested against a specific matrix of native module
versions. Packages outside that matrix are prone to native/JS API mismatches —
crashes, missing methods, or build failures — that only show up at runtime or in
a native build, not in TypeScript.

**Fix:** `npx expo install --fix`, which resolved and installed the
SDK-53-compatible versions via `yarn` (the project's active package manager —
confirmed via `node_modules/.yarn-integrity`) and updated `package.json` /
`yarn.lock`. It also auto-registered `@react-native-community/datetimepicker`
and `expo-web-browser` as config plugins in `app.json`, since newer versions of
those packages require plugin-based native config.

## 2. Metro crash: "Cannot read properties of undefined (reading 'transformFile')"

**Symptom:** Every bundle request failed with a red-box error at
`node_modules/metro/src/Bundler.js:44`, with no useful detail in the IDE's error
panel.

**Root cause:** Running Metro directly (not through the IDE's swallowed error
panel) surfaced the real exception:

```
Failed to construct transformer:  TypeError: (0 , metro_cache_key_1.default) is not a function
    at Object.getCacheKey (@expo/metro-config/src/transform-worker/metro-transform-worker.ts:780:36)
```

Every `metro-*` package in `node_modules` was consistently pinned to `0.82.5`
**except** `metro-cache-key`, which had been hoisted to `0.84.4`. That version
bump changed the package's export shape from a default `module.exports = fn` to
a named export (`exports.getCacheKey = fn`), so `@expo/metro-config` (built
against the old shape) called `undefined()` and silently failed to construct
the transformer — Metro then hit `this._transformer.transformFile()` on an
undefined transformer for every request.

The stray `0.84.4` came from `react-native-dynamic`'s dependency on
`@types/react-native`, a deprecated stub types package whose own
`dependencies` field is `{"react-native": "*"}` — a wildcard that resolved to
a much newer `react-native` (0.86.2) at install time, dragging in its newer
`metro`/`metro-cache-key` as transitive deps, which yarn then hoisted over the
correct version.

**Fix:** Pinned the version via yarn's `resolutions` field in `package.json`:

```json
"resolutions": {
  "metro-cache-key": "0.82.5"
}
```

then `yarn install` and a full Metro restart with `--clear` (existing Metro
processes had already loaded the broken module into memory, so killing and
restarting was required — editing `node_modules` on disk doesn't affect an
already-running process).

## 3. Missing dependency: `react-native-purchases`

**Symptom:** Once Metro's transformer was fixed, bundling failed on a new,
unrelated error: `Unable to resolve module react-native-purchases from
services/revenueCatService.ts`.

**Root cause:** `services/revenueCatService.ts` statically imports
`react-native-purchases`, and `README_REVENUECAT_SETUP.md` claims the "RevenueCat
SDK integrated in app code" step is already done — but the package was never
actually added to `package.json`. It's likely the file was written/copied in
without ever running the install step.

**Fix:** `npx expo install react-native-purchases` — installed `10.7.0` (SDK-53
compatible) and added it to `package.json`.

**Follow-up to be aware of:** `MOCK_IAP` in `constants/featureFlags.ts` is set
to `false`, meaning the app expects real native purchases. `react-native-purchases`
contains native iOS/Android code and is **not supported in Expo Go** — the app
currently falls back to "RevenueCat in Browser Mode" when run there (see log
line `Expo Go app detected. Using RevenueCat in Browser Mode.`). To actually
exercise real purchase flows you'll need a custom dev client build (`eas.json`
already has a `development` profile with `developmentClient: true` ready to use).
